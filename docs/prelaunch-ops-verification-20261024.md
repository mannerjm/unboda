## A. 관리자 카드 환불 운영 경로 — 실제 운영 읽기 점검

### 코드·설정 확인 (금전 미실행)

- 환불 신청 고객: 운보다 마이페이지 결제 내역에서 `환불·취소 문의` → 고객지원 센터에서 `PAYMENT_REFUND`와 주문을 연결해 접수.
- 관리자: `/admin/support`에서 문의를 찾아 `IN_REVIEW`로 전환하고 구체적인 법정·계약상 사유를 선택.
- 운영 API: `app/api/internal/admin/report-refunds/route.ts`는 `requireOperator`, `REPORT_REFUND_APPROVER_IDS`(서버 UUID allowlist), `isFinancialMfaVerified`(추가 인증) 요구.
- 사전 조회: 본인 주문과 문의 연결, 정확한 상품·에디션·결제 금액, 토스 `DONE` 원결제, 부분/전체 취소 이력 0건, 일반 전액 환불 정책 대상 여부 대조. `GET`은 실제 취소를 실행하지 않음.
- 실제 승인: 운영자 명시적 재확인·금액 일치·사유 기록 후 POST에서 모든 검사를 반복하고 감사 기록 저장 후 `requestFullRefund`를 호출. 작업 고유 키를 통해 환불 워크플로를 추적하고 구매 이용권을 회수.
- 결과 불명확/통신 장애/정산 오류: **재승인 버튼 재클릭 금지**. 토스 원결제와 `refund_workflows` 및 복구 워커를 우선 확인하고 DB 결제 기록 직접 수정 금지.
- 생산 DB 검증 (2026-10-24 KST): 승인자로 등록된 UUID 1개 = 실제 활성 관리자 계정 1개, 해당 인증 사용자에 `verified` MFA 요소 존재, 다른 계정에 이 환불 권한 자동 부여하지 않음. 다만 현재 브라우저 세션의 AAL2 및 승인화면의 실제 동작은 별도로 검사해야 함.
- `REPORT_REFUND_ADMIN_ENABLED=false`. 실결제 환불을 고객용으로 공개 전, 고객지원 주문이 연결된 합성/격리 테스트로 단계별 운영자 경로를 재검증하고 정식 판매에 필요한 환불 담당자의 장애 대응 권한과 의사결정 책임자를 확인해야 함. 이미 취소된 LIVE 주문에 재취소 금지.

### 운영자 브라우저 최종 수동 점검 (운영에서 재취소 금지)

1. 허가되지 않은 계정에서 `/admin/support` 및 환불 실행 API가 차단되는지 검증.
2. 허가 관리자 로그인 → `/admin/mfa`의 인증 앱 AAL2 완료 → 고객지원 메뉴 진입.
3. 기존 취소 완료 주문의 문의를 조회할 경우 **중복 환불 불가**가 표시되는지 읽기 전용으로 확인. 임의로 새로운 구매자 실제 주문을 만들거나 결제 취소를 호출하지 않음.
4. 별도의 staging/격리 환경에 합성 문의·결제를 만들어 정책 거절/잘못된 금액/CSRF/토스 장애/감사 로그 실패/중복 재실행 차단을 검증. `scripts/admin-report-refund-safety-regression.cjs`의 합성 결과는 실제 운영 환불을 대체하지 않음.
5. 오픈 시 고객지원 답변 담당자와 실제 환불 승인 담당자, 미처리 건 일일 확인 책임자 지정.

## C. 백업 및 격리 복구 — 미완료, 출시 전 실증 필요

운영 프로젝트: Supabase Production. **연결된 앱 도구에서 백업 목록·보유 기간·PITR 활성 여부를 확인할 기능이 없어 현재 자동 백업·복구 성공은 검증하지 못했다.**

1. Supabase 운영 대시보드 `Database → Backups` 에서 최근 성공 백업 시각, 보관 기간, 사용 요금제 및 PITR 활성/복구 지점을 확인해 증거 저장.
2. DB 백업은 Storage 버킷의 **실제 객체 바이너리를 포함하지 않을 수 있음**. Storage 객체 유무 및 별도 보존 방식을 확인.
3. Production에 직접 복원하지 말 것. 별도의 격리 프로젝트·안전한 복원 환경을 먼저 계획하고, 필요한 경우 생성 비용·데이터 취급 범위를 사전 승인받기. 복원 환경은 서비스 외부에 공개하지 말고 테스트 종료 시 정리.
4. 실제 백업 복원을 격리 환경에만 수행하고 Auth·프로필·주문·환불 워크플로·리포트·이용권 간 건수 및 FK 무결성, 권한 차단을 읽기 검사. 카드 API 실결제/환불 및 AI 외부 호출을 차단.
5. 실제 복원 성공 시각, 백업 기준 시각, 복구 소요시간, 장애 시 데이터 유실 가능 범위(RPO/RTO), 검증자와 결과를 문서화. **화면상 백업 존재만으로 복원 성공 처리하지 않음.**

공식 자료: https://supabase.com/docs/guides/platform/backups 및 https://supabase.com/docs/guides/platform/clone-project

## D. 모바일·계정·프로필 E2E — 실제 브라우저 검증 미완료

정적 검사 및 Supabase DB 구조에서 `orders`, `purchases`, `entitlements`, `paid_reports`의 `profile_id NOT NULL` 및 주문/구매/이용권 프로필 연결 FK를 확인. 서버가 `user_id + profile_id`로 entitlement를 조회함을 확인했다. 이는 브라우저 실사용 E2E의 대체가 아님.

**테스트에 필요한 환경:** 실제 PC Chrome, iPhone Safari, Android Chrome 또는 동등한 실제 디바이스/브라우저 세션, 본인 테스트 계정 A, 독립 사용자 계정 B, 본인 프로필 P1 및 배우자 프로필 P2. 인증정보/비밀번호/결제카드정보를 캡처하거나 테스트 로그에 기록하지 않음.

1. 비회원 → 무료 사주 입력: 휴대전화 320~390px 뷰포트, 출생 시각 모름 체크, 양/음력·윤달, 저장/회원 전환, 키보드 표시 시 버튼 가림 여부.
2. 첫 회원 A → 이메일 확인 → NICE 실제 상용 성인인증. 새 계정의 실제 인증 프로세스, 미성년·취소·실패 처리 여부는 인증 서비스와 계약 조건 내에서 별도 시험.
3. A 본인 P1으로 무료 분석 후 유료 구매 화면: 선택된 분석대상·상품/에디션·가격·디지털 콘텐츠 즉시 제공/청약철회 고지·동의 체크·결제 버튼 상태·다중 탭 중복 주문 방지 확인. 일반 LIVE 판매 OFF 상태에서 실결제 불가가 정상.
4. P1에 기존 구매·권한이 있는 경우 리포트 열람 허용 확인 → P2 전환 → 같은 제품 미구매 안내 및 P1 본문 차단 확인 → P2 별도 구매 가능 UI 확인 → 다시 P1로 전환 후 원래 권한 표시 확인. **각 프로필에 권한이 있음을 독립적으로 가정하지 말 것.**
5. 계정 B로 로그인 → A의 URL을 붙여 넣어도 리포트/AI 상담·기억/구매·고객지원 정보 열람이 차단되는지 확인. 브라우저 뒤로 가기 및 재접속 캐시도 검사.
6. 결제 완료·환불 완료 내역 및 구매 보관함 회수 화면을 작은 화면에서 확인. 이미 취소한 9,900원 LIVE 주문은 반복 환불하지 않음.
7. AI 상담 진입·질문권 구매 UI·횟수 차감·가용 질문권·지원 문의·고객 답변 확인. 실제 고객 카드 결제 및 질문권 자동 카드 부분취소는 별도 명시적 승인 전까지 실행 금지.
8. 테스트별 스크린샷과 기기·브라우저 버전, 통과/실패, 재현 단계만 안전하게 기록. 단순 화면 스크립트/Next.js 빌드 통과를 실제 모바일 E2E 완료로 쓰지 않음.

## F. 전체 LIVE 결제 개방 금지/허용 게이트

- 필수: 환불 담당자·승인자의 실제 브라우저 운영 절차 및 장애 대응 책임 확인, 개인정보 정책 미확정 사실 해소, 백업 존재와 **격리 복구 실증**, 모바일·프로필·독립 계정 실사용 시나리오 통과.
- 정식 결제 개방을 위한 **별도 명시적 최종 승인** 전에 `TOSS_LIVE_CHECKOUT_ENABLED` 수정 금지. 권한 검증을 대신하는 임시 환불 우회도 금지.
- 사용자 요구대로 현대카드 심사 대기 사항을 고객 화면에 별도 안내로 띄우지 않음. 승인이 확인되기 전까지 승인되지 않은 카드의 지원을 보장하는 문구 역시 추가하지 않음.
- 운영 배포는 PR/빌드/미리보기 검증을 거쳐 변경된 코드의 Production READY와 도메인 연결을 확인하고 완료 선언.
